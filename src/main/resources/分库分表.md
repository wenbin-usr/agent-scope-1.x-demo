# 分库分表全面解析

---

## 一、分库分表的作用

### 1. 为什么要分库分表？

随着业务增长，单库单表面临以下瓶颈：

| 痛点 | 具体表现 |
|------|----------|
| **存储瓶颈** | 单表数据量过大（千万级+），磁盘空间不足 |
| **查询瓶颈** | B+树层级增加，索引查找变慢；全表扫描代价大 |
| **写入瓶颈** | 高并发写入导致锁竞争激烈，TPS下降 |
| **连接瓶颈** | 单库最大连接数有限，并发请求排队 |
| **可用性瓶颈** | 单库宕机 = 全业务不可用 |

> **核心目标**：将数据分散到多个物理节点，降低单节点压力，提升整体吞吐量和可用性。

## 二、分库分表怎么实现

### 1. 拆分维度

```
┌─────────────────────────────────────────────┐
│              拆分策略总览                      │
├─────────────┬───────────────────────────────┤
│  垂直拆分    │  水平拆分                       │
├─────────────┼───────────────────────────────┤
│  垂直分库    │  水平分库                       │
│ (按业务拆库) │ (相同结构，数据分散到多库)       │
├─────────────┼───────────────────────────────┤
│  垂直分表    │  水平分表                       │
│ (按字段拆表) │ (相同结构，数据分散到多表)       │
└─────────────┴───────────────────────────────┘
```

#### 🔹 垂直分库（按业务拆）
```
单库 db_all
  ├── 用户表、订单表、商品表、支付表...

↓ 拆分 ↓

db_user   → 用户相关表
db_order  → 订单相关表
db_product → 商品相关表
db_pay    → 支付相关表
```
- **原理**：不同业务耦合度低，拆到独立库，各自独立扩容
- **适用**：微服务架构，业务边界清晰

#### 🔹 垂直分表（按字段拆）
```
单表 t_user (100个字段)
  ├── 常用字段：id, name, age, phone
  ├── 不常用：avatar, bio, address, settings...

↓ 拆分 ↓

t_user_base    → id, name, age, phone (高频访问)
t_user_detail  → id, avatar, bio, address (低频访问)
```
- **原理**：将热数据/冷数据分离，减少单行大小，提高缓存命中率
- **适用**：字段多、行数据大、热点字段集中的表

#### 🔹 水平分库（相同结构，分散到不同库）
```
db_0 → t_order (0 ~ 1000万)
db_1 → t_order (1000万 ~ 2000万)
db_2 → t_order (2000万 ~ 3000万)
```
- **原理**：多库承担不同数据段，分摊写入和查询压力
- **适用**：单库数据量/写入量超限

#### 🔹 水平分表（相同结构，同一库多张表）
```
同一库 db_order 中：
  t_order_0 → 数据段 A
  t_order_1 → 数据段 B
  t_order_2 → 数据段 C
```
- **原理**：单库容量够但单表太大，拆表降低单表数据量
- **适用**：单表数据量大，但库级压力还没到极限

> **实战中最常用的是：水平分库 + 水平分表组合**

### 2. 分片键与分片算法

**分片键**：决定数据落到哪个分片的核心字段（如 `user_id`, `order_id`）

**常见分片算法**：

| 算法 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| **Hash取模** | `shard = hash(key) % N` | 数据分布均匀 | 扩缩分片需数据迁移 |
| **范围分片** | `id 1~1M → shard_0, 1M~2M → shard_1` | 扩容方便（加新范围） | 数据可能倾斜（热点范围） |
| **一致性Hash** | 虚拟节点环，减少迁移量 | 扩缩容迁移量少 | 实现稍复杂 |
| **枚举/查找表** | 配置映射：region=北京→shard_0 | 业务语义清晰 | 维护映射表 |
| **混合策略** | 如先按地区枚举，再按ID取模 | 兼顾业务语义与均匀性 | 配置复杂 |

---

### 3. 实现分库分表的代码示例（以取模为例）

```java
// 分片路由逻辑伪代码
public String getTableName(long userId) {
    int shardCount = 4; // 分表数量
    int index = (int) (userId % shardCount);
    return "t_order_" + index;
}

// 查询路由
public List<Order> queryByUserId(long userId) {
    String tableName = getTableName(userId);
    return jdbcTemplate.query("SELECT * FROM " + tableName + " WHERE user_id = ?", ...);
}
```

> ❌ 问题：业务代码侵入太深，每个 SQL 都要手动路由

这就是为什么需要 **分库分表中间件**！

### 1. Apache ShardingSphere（当前最主流）

#### 架构模式

```
┌─────────── ShardingSphere 两种形态 ───────────┐
│                                                │
│  📦 ShardingSphere-JDBC（Client端）            │
│  ┌──────────────────────────────────────┐     │
│  │  Application                        │     │
│  │    ↓                                │     │
│  │  ShardingSphere-JDBC (JAR包)        │     │
│  │    ↓  增强DataSource                │     │
│  │  真实 DataSource → DB0, DB1, DB2    │     │
│  └──────────────────────────────────────┘     │
│  优点：无中间层、性能高、零部署成本             │
│  缺点：每应用需配置、仅限Java                   │
│                                                │
│  🖥️ ShardingSphere-Proxy（Proxy端）            │
│  ┌──────────────────────────────────────┐     │
│  │  Application → MySQL协议 → Proxy    │     │
│  │    ↓                                │     │
│  │  Proxy解析SQL → 路由改写 → 多DB      │     │
│  └──────────────────────────────────────┘     │
│  优点：对应用透明、异语言接入                   │
│  缺点：多一层网络转发、性能损耗                 │
└────────────────────────────────────────────────┘
```

#### 核心实现原理（四大阶段）

```
  SQL输入
    │
    ▼
┌─────────────┐
│ ① SQL解析    │  → 解析为AST语法树（使用Calcite/ANTLR）
└─────────────┘
    │
    ▼
┌─────────────┐
│ ② SQL路由    │  → 根据分片键+分片算法，确定目标分片
│              │     筛选出需要执行的逻辑表→物理表映射
└─────────────┘
    │
    ▼
┌─────────────┐
│ ③ SQL改写    │  → 将逻辑表名替换为物理表名
│              │     如 t_order → t_order_0
│              │     修正聚合函数、LIMIT等
└─────────────┘
    │
    ▼
┌─────────────┐
│ ④ SQL执行    │  → 并行发到多个真实DataSource执行
│              │     结果归并：流式归并/内存归并
└─────────────┘
    │
    ▼
  返回结果
```

#### 配置示例（Spring Boot + ShardingSphere-JDBC）

```yaml
# application-sharding.yml
spring:
  shardingsphere:
    datasource:
      names: ds0, ds1
      ds0:
        type: com.zaxxer.hikari.HikariDataSource
        driver-class-name: com.mysql.cj.jdbc.Driver
        jdbc-url: jdbc:mysql://localhost:3306/db0
        username: root
        password: root
      ds1:
        type: com.zaxxer.hikari.HikariDataSource
        driver-class-name: com.mysql.cj.jdbc.Driver
        jdbc-url: jdbc:mysql://localhost:3306/db1
        username: root
        password: root

    rules:
      sharding:
        tables:
          t_order:  # 逻辑表名
            actual-data-nodes: ds0.t_order_0, ds0.t_order_1, ds1.t_order_0, ds1.t_order_1
            table-strategy:
              standard:
                sharding-column: user_id
                sharding-algorithm-name: order-table-mod
            database-strategy:
              standard:
                sharding-column: user_id
                sharding-algorithm-name: order-db-mod
        sharding-algorithms:
          order-table-mod:
            type: MOD
            props:
              sharding-count: 2
          order-db-mod:
            type: MOD
            props:
              sharding-count: 2
```

业务代码 **完全无感知**：

```java
// 和普通MyBatis/JPA写法一模一样！
@Select("SELECT * FROM t_order WHERE user_id = #{userId}")
List<Order> findByUserId(Long userId);
// ShardingSphere自动路由到 t_order_0 或 t_order_1，ds0 或 ds1
```

### 2. MyCat

#### 实现原理

```
  应用 → MySQL协议 → MyCat(Server)
                          │
                    ┌─────┼─────┐
                    │     │     │
                  DB0   DB1   DB2

MyCat核心流程：
1. 作为MySQL代理服务器，应用连接MyCat（伪装成MySQL）
2. 接收SQL → 解析（Druid Parser）
3. 根据rule.xml分片规则路由
4. 改写SQL发到后端MySQL实例
5. 合并结果返回给应用
```

**关键配置**：
- `server.xml`：MyCat服务配置（用户、权限、端口）
- `schema.xml`：逻辑库、逻辑表、物理节点映射
- `rule.xml`：分片规则（分片键、分片算法）

```xml
<!-- rule.xml 示例 -->
<tableRule name="order_mod">
    <rule>
        <columns>user_id</columns>
        <algorithm>mod-long</algorithm>
    </rule>
</tableRule>

<function name="mod-long" class="io.mycat.route.function.PartitionByMod">
    <property name="count">4</property>
</function>
```

### 3. Vitess（YouTube开源，云原生方向）

```
  应用 → VTGate（代理层，MySQL协议）
              │
        ┌─────┼─────┐
      VTTablet  VTTablet  VTTablet  （每个分片一个）
        │        │        │
       MySQL    MySQL    MySQL

核心概念：
- VTGate：无状态代理，SQL解析+路由+合并
- VTTablet：每个MySQL实例的sidecar代理
- VSchema：分片拓扑定义
- VReplication：分片迁移与在线扩容工具
```

**特色**：
- 基于 VIndex（类似分片键）定义路由规则
- 支持在线 Resharding（动态扩缩分片，数据自动迁移）
- 云原生，Kubernetes 集成良好

### 4. Client端 vs Proxy端 架构对比

```
                    Client端                      Proxy端
               ┌────────────────┐          ┌────────────────┐
               │   App          │          │   App          │
               │     ↓          │          │     ↓          │
               │  Sharding      │          │  Proxy Server  │
               │  JDBC(JAR)     │          │  (独立进程)     │
               │     ↓          │          │     ↓          │
               │  DB0 DB1 DB2   │          │  DB0 DB1 DB2   │
               └────────────────┘          └────────────────┘

性能损耗：    低（直连DB）                  多一跳网络（~10-20%损耗）
部署成本：    低（JAR引入）                 需独立部署+运维
语言限制：    仅Java                        任意语言（MySQL协议）
运维管理：    各应用独立配置                 统一管理，对业务透明
高可用：      依赖应用侧                    Proxy自身也要HA
适用场景：    Java微服务                    多语言/老系统/统一管控
```

## 四、分库分表的挑战与解决方案

| 挑战 | 说明 | 解决方案 |
|------|------|----------|
| **跨分片JOIN** | 不同分片的数据无法直接JOIN | ① 全局表（广播到每个分片）② ER分片（绑定关联表到同分片）③ 应用层组装 |
| **分布式排序** | ORDER BY需跨分片合并排序 | 中间件流式归并（归并排序算法） |
| **分布式聚合** | COUNT/SUM/AVG需跨分片累加 | 中间件改写为各分片聚合，再二次聚合 |
| **跨分片分页** | LIMIT偏移大时性能差 | ① 各分片取 OFFSET+LIMIT 再合并 ② 游标分页 |
| **全局唯一ID** | 自增ID在各分片冲突 | ① Snowflake算法 ② 号段模式 ③ UUID ④ Redis自增 |
| **分布式事务** | 跨分片写入需保证一致性 | ① 本地事务+最终一致性 ② XA强一致 ③ Seata AT/TCC |
| **数据迁移/扩容** | 加分片需迁移旧数据 | ① 一致性Hash减少迁移 ② 双写+灰度切换 ③ Vitess Resharding |
| **非分片键查询** | 查询条件不含分片键→全分片扫描 | ① 建立映射表(基因法) ② 引入ES做二级索引 ③ 合理选分片键 |

## 五、选型建议

```
                    ┌─ 是否只用Java？
                    │   YES → ShardingSphere-JDBC
                    │   NO  → ShardingSphere-Proxy 或 Vitess
                    │
                    ├─ 是否云原生/K8s环境？
                    │   YES → Vitess
                    │   NO  → ShardingSphere
                    │
                    ├─ 是否需要在线扩缩分片？
                    │   YES → Vitess（Resharding）
                    │   NO  → ShardingSphere
                    │
                    ├─ 是否老系统改造（不改代码）？
                    │   YES → Proxy模式
                    │   NO  → JDBC模式
                    │
                    └─ 数据规模？
                        百万级 → 先优化SQL/索引，不必分片
                        千万级 → 先考虑读写分离
                        亿级   → 分库分表
```

## 总结

| 关键要点 |
|----------|
| 分库分表的本质是 **用空间换时间、用分布换并发** |
| **水平分库+水平分表** 是最常见的组合策略 |
| **分片键** 是成败关键——选不好，全分片扫描比不分片还慢 |
| **ShardingSphere** 是当前最成熟、最活跃的中间件（JDBC/Proxy双形态） |
| 分库分表带来 **分布式事务、跨片查询、全局ID、扩容迁移** 等新难题 |
| **优先级**：先SQL优化 → 读写分离 → 缓存 → 分库分表（最后手段） |
| 如果数据量可预估，**TiDB/CockroachDB** 等NewSQL也是替代方案（自动分片，透明分布式） |

> 💡 **一句话**：分库分表不是银弹，是最后的手段。能不分就不分，非要分就选好分片键、选好中间件、提前规划扩容方案。
